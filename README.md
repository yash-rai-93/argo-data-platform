# Project ARGO

**A decision-intelligence platform that predicts *when* an open-source contributor will go quiet — trained on 547,434 real GitHub Archive events, and prepared to defend every number it produces.**

---

## Executive Summary

Maintainer attrition is the dominant failure mode of open-source infrastructure. A project does not die when its issue count spikes; it dies when the three people who understand the build system quietly stop showing up. That signal is buried in event streams nobody aggregates.

ARGO answers a concrete, falsifiable question:

> **Given a contributor's behaviour across a four-month observation window, how long until they lapse — and who is decaying fastest right now?**

Every number here comes from `githubarchive.day.*`: real pushes, real pull requests, real reviews, from a curated cohort of 24 production Python repositories (`pytorch/pytorch`, `python/cpython`, `pandas-dev/pandas`, `apache/airflow`, `huggingface/transformers`, …). There is no synthetic data anywhere in this repository.

| Source events | 547,434 (2023-07-01 → 2024-01-01) |

## The Central Argument: Why 0.70 Beats 0.97

**The first version of this model scored ROC-AUC 0.97. It was thrown away.**

That model was trained on synthetic events generated by a script in this same repository. The generator wrote churn into the data according to a rule; the model learned the rule. A 0.97 on self-generated data proves only that gradient boosting can invert a function you handed it. The correct response to that number is not celebration — it is deletion.

The full, unedited history is committed to `meta_model_registry` and rendered in the dashboard. Nothing here is retconned:

| Version | Features | Rows | CV | Holdout | Precision | Recall |
| --- | --- | --- | --- | --- | --- | --- |
| `v0.1-synthetic` | 3 | 1,000 | — | **0.9700** | — | — |
| `v1.0-github-raw` | 13 | 54,613 | 0.7020 | 0.6620 | 0.9269 | 0.8988 |
| `v2.0-eligibility-floor` | 13 | 3,033 | 0.8089 | 0.7399 | 0.7609 | 0.6243 |
| `v2.1-regularized` | 16 | 3,033 | 0.8131 | 0.7563 | 0.7616 | 0.7238 |
| `v2.2-boundary-probe` | 16 | 3,033 | 0.8137 | 0.7553 | 0.7704 | 0.6768 |
| **`v3.0-survival-cox`** | 16 | 3,033 | **0.8522** (C) | **0.7005** (C) | n/a | n/a |

Two rows carry `comparable = false`. `v0.1` scored a different target on data that no longer exists. `v3.0` reports a concordance index, which is **not** an ROC-AUC — plotting them on one axis would repeat the original error in a new form.

### The precision drop was the victory

Look at `v1.0` → `v2.0`. Precision falls from **0.9269 to 0.7609**. On a dashboard that reads as catastrophic regression. It was the single most valuable change in the project.

The raw GitHub cohort is **54,613 contributors at a 91.6% churn rate**, dominated by drive-by first-timers who open one pull request and vanish. At that base rate, a model that predicts "everyone churns" scores ~92% precision while knowing nothing. **The 0.9269 was measuring the class distribution, not the model.**

The eligibility floor — enforced in SQL, not in Python — removes them:

```sql
having count(*) >= 5
    and count(distinct cast(o.created_at as date)) >= 3
```

The cohort collapses to 3,033 contributors at a 59.6% holdout churn rate. Precision falls to 0.76 because the problem became genuinely hard. **ROC-AUC rose 0.662 → 0.740 over the same change**, which is the metric that was not being inflated by the base rate.

A model that is worse on a lying metric and better on an honest one has improved. Reporting only the first number is how portfolio projects get built; reporting both is the point of this one.

## Machine Learning Architecture

### Why survival analysis, not classification

Binary classification asks *will this contributor churn?* Every training row must be labelled yes or no. That requirement is the problem.

Of 2,426 training contributors, **1,186 were still active when the observation window closed**. Their outcome is genuinely unknown — they are **right-censored**. A classifier is forced to label them "retained", which is true only up to the cutoff. It cannot represent *"still contributing on day 184, outcome unobserved."* Nearly half the dataset is being asserted as fact when it is actually a truncation artifact.

Cox proportional hazards handles this natively: a censored subject contributes to the risk set until the moment of censoring and no further. Nothing is fabricated and nothing is discarded.

The model also answers the more useful question. A maintainer does not need a probability with a threshold nobody agreed on; they need to know **who is decaying fastest and how long is left**.

### Label encoding

XGBoost's `survival:cox` objective takes a single signed target:

```
y = +duration    observed event (contributor lapsed)
y = -duration    right-censored (still active at the study cutoff)
```

`duration` is emitted by the dbt mart:

```sql
case
    when t.actor_login is null
        then date_diff('day', f.first_event_at, f.last_event_at)   -- lapsed
    else date_diff('day', f.first_event_at, b.target_end)          -- censored
end as duration
```

**Censored subjects must run to `target_end`, not to their last observed event.** Ending their clock early reports a shorter survival time than was actually observed and biases every hazard estimate downward. This is subtle, silent, and wrong in a way no test catches unless you write one.

`scale_pos_weight` is deliberately absent. The Cox partial likelihood already accounts for censoring through the risk set; reweighting classes on top of it distorts the hazard rather than balancing anything.

### Harrell's C-index

ROC-AUC requires a hard label at a fixed horizon, which means discarding every censored subject — precisely the population survival analysis exists to serve. The concordance index replaces it:

> Over all *comparable* pairs — where one subject is known to have failed before the other's last observation — how often does the model rank the one who lapsed first as the riskier of the two?

0.5 is a coin flip; 1.0 is perfect ordering. Scored via `sksurv.metrics.concordance_index_censored`.

**Holdout C-index: 0.7005.** Cross-validated: 0.8522. That 0.15 gap is real temporal generalisation loss, exposed on purpose by the chronological split.

### The Breslow baseline estimator

`survival:cox` predicts a **hazard ratio and nothing else**. There is no baseline hazard stored in the artifact, so $P(T > t)$ is not recoverable from `predict()` alone. Rendering a survival curve without solving this would mean inventing one.

The API reconstructs the baseline with the Breslow estimator, computed from the **training split only** and cached at startup:

$$d\hat{H}_0(t) = \frac{d(t)}{\sum_{j \in R(t)} \widehat{HR}_j} \qquad\qquad S(t \mid x) = S_0(t)^{\widehat{HR}(x)}$$

Evaluated on a 37-point grid across the 180-day horizon, then scaled per contributor at request time:

| Scenario | Hazard ratio | Day 30 | Day 60 | Day 90 | Median survival |
| --- | --- | --- | --- | --- | --- |
| Fading core maintainer | 1.12× | 79% | 64% | 51% | **95 days** |
| Thriving contributor | 0.43× | 91% | 84% | 77% | never (180d+) |

### Model validation

`ml/evaluate_model.py` replaces the confusion matrix with **Kaplan-Meier curves stratified by predicted risk tercile** — the survival equivalent. If the model ranks correctly, the high-risk curve falls fastest and the three bands never cross. They don't: the low tercile plateaus near 69% survival, the medium near 38%, the high near 20%.

SHAP `TreeExplainer` provides per-prediction attribution over the log-hazard, cached in the FastAPI lifespan handler so the first request pays no tree-traversal setup cost.

### The dual-model architecture

Both models are live and serve different surfaces:

| Model | Artifact | Serves | Metric |
| --- | --- | --- | --- |
| Cox survival | `churn_cox.json` | Triage queue, survival curves, urgency bands | C-index 0.7005 |
| Binary classifier | `churn_xgb.json` | Threshold simulator, SHAP margin decomposition | ROC-AUC 0.7553 |

The classifier was preserved rather than deleted because a threshold-sweep confusion matrix is a legitimate artifact that a hazard ratio cannot produce — Cox emits an unbounded ratio with no decision boundary. `ml/train_classifier.py` keeps it regenerable.

## Data Layer

```
Extraction              Warehouse                    Modelling                Serving        Presentation
─────────────────       ────────────────────────     ───────────────────      ──────────     ──────────────
BigQuery                dbt 1.12 + DuckDB        ─▶  XGBoost survival:cox ─▶  FastAPI    ─▶  Next.js 16
githubarchive.day.  ─▶  raw_github_events (547k)     Breslow baseline         /predict       React 19
  2023*                   ↓                          SHAP TreeExplainer       /metrics       Tailwind v4
  partition-pruned      ml_contributor_churn_        chronological holdout    /customers     Recharts
  column-pruned           training (3,033)           STL(period=7)            /governance
  PyArrow zero-copy     metric_contributor_
                          retention (21 cells)
                        metric_activity_
                          decomposition (184d)
                        meta_model_registry
                        meta_dbt_runs
```

**Stage 1 — Extraction.** `sql/bigquery/extract_python_contributor_events.sql` reads `githubarchive.day.2023*` with `_TABLE_SUFFIX` partition pruning. The wildcard is anchored to a year prefix because the bare `day.*` form also matches the dataset's logical views (`yesterday`, `today`), whose schema mismatch raises a 400 BadRequest. `SELECT *` is never used — the nested `payload` JSON dominates dataset size and is never referenced. Bots are filtered at source.

**Stage 2 — Landing.** `etl/land_github_data.py` moves results into DuckDB through Arrow with no intermediate serialisation: `job.to_arrow()` → `connection.register()` → `CREATE OR REPLACE TABLE`. No CSV round-trip, no pandas materialisation, no dtype coercion bugs. Both engines speak Arrow natively; the bytes are shared, not copied.

**Stage 3 — Transformation.** dbt materialises the marts. Observation and target windows are declared **once** in a `bounds` CTE and enforced as half-open `[start, end)` intervals; derived cutoffs (window midpoint, trailing-30-day boundary) are computed from those bounds rather than hardcoded, so moving a boundary moves everything downstream. Events are deduplicated on `event_id` via `QUALIFY` because GitHub Archive replays them.

**Stage 4 — Serving.** An import-time assertion compares the Pydantic request schema against `FEATURE_COLUMNS` field-by-field; **the application refuses to boot on drift**.

### Why DuckDB over Postgres

The default resume-driven answer is "put it in Postgres." That answer is wrong here, and the reasoning matters more than the choice.

**This workload has zero write paths.** ARGO never issues an `UPDATE`, never opens an interactive transaction, and never serves a point lookup by primary key. It executes wide analytical scans — `count(*) FILTER (WHERE event_category = ...)` across half a million rows, grouped by contributor. That is precisely the access pattern row-stores are worst at.

| Dimension | DuckDB | Postgres |
| --- | --- | --- |
| Storage layout | Columnar, compressed | Row-major heap pages |
| Scanning 6 of 13 columns | Reads 6 columns | Reads every column in every touched page |
| Execution | Vectorised, SIMD, multi-core by default | Tuple-at-a-time; parallelism opt-in |
| Aggregating 547k rows | 0.05s, single process | Index strategy, tuning, or a read replica |
| Operational surface | One file | Server process, WAL, vacuum, pooling, backups |
| Distribution | `git clone` and it works | Managed service, network hop, credential rotation |

**The concurrency objection is real and does not apply.** Postgres wins decisively on concurrent writers and transactional integrity. ARGO has exactly one writer — the ETL script, run offline — and N readers, all opening the file `read_only=True`. Paying a row-store's scan penalty *plus* operational overhead to buy MVCC guarantees nothing in this system requires is a straight loss.

Those timings are measured on this warehouse: a six-column grouped aggregate with two `FILTER` clauses over all 547,434 rows returns in 0.05s, and `dbt build` materialises the full training mart — dedupe, windowing, sixteen features, both target encodings — in 0.26s, as recorded in `meta_dbt_runs`.

**The migration cost is not hypothetical.** The dbt layer leans on DuckDB-native constructs: `QUALIFY` for deduplication, `arg_max` for last-seen repo attribution, `count(*) FILTER` for categorical rollups, `date_diff`/`to_days` anchored to window boundaries. Porting means rewriting every mart into window-function subqueries for no measured gain.

**Single-file portability is a feature, not a consolation.** The 13 MB warehouse is committed to this repository. A reviewer clones and serves a prediction in under a minute with no database to provision, no credentials, and no ETL run. That property is unavailable from any server-based engine.

**When this decision flips:** the moment a write path appears — user annotations, feedback loops, multi-tenant state. The correct move then is Postgres for the OLTP surface *alongside* the columnar store, not migrating analytics into an engine that is bad at it.

### Why chronological splitting over random sampling

**A random split on temporal data is a leak, and it is the most common quietly-fatal bug in applied ML.**

`train_test_split(shuffle=True)` scatters contributors from every era across both sets. Training then contains contributors whose activity is *contemporaneous with* — and correlated with — the test set: the same release cycles, the same CVE scrambles, the same conference-season lulls, the same repository policy changes. The model learns period-specific artifacts and is graded on the period it memorised. The reported score measures the split, not the model.

ARGO sorts by `first_event_at` ascending and cuts 80/20:

```python
cutoff = int(len(frame) * _SPLIT_RATIO)
train = frame.iloc[:cutoff]
test = frame.iloc[cutoff:]
```

Training sees only contributors who joined before **2023-09-06**. Evaluation happens exclusively on the newest cohort, one the model has no temporal adjacency to. **This reproduces the deployment condition:** in production the model always scores contributors who arrived after the training data was frozen.

Three reinforcing controls:

- Grid-search cross-validation uses `TimeSeriesSplit(n_splits=3)` — expanding-window forward chaining, where every validation fold is strictly later than the folds that trained it.
- `first_event_at` is projected for ordering only. `enforce_schema` restricts the matrix to `FEATURE_COLUMNS`, which excludes it, so **the split key cannot become a feature**.
- `days_since_last_event` is anchored to `observation_end`, **never** to `max(created_at)`. Anchoring to the observed maximum makes recency non-comparable across contributors and smuggles future information into a feature that looks innocent. That single line separates a defensible model from a 0.99 fantasy.

**The measured cost of honesty: CV 0.8522 → holdout 0.7005.** That gap is the leak, quantified, reported rather than hidden.

### Leakage is asserted, not assumed

`transform/tests/assert_no_target_leakage.sql` recomputes the mart's aggregates directly from `raw_github_events` restricted to the observation window and fails on any disagreement. It is a real test, not a tautology: widening the feature window to `target_end` makes it flag **1,431 of 3,033 rows**.

`tests/test_contract.py` asserts that the Pydantic schema, the trained feature list, and the display-label map are the same 16 columns in the same order — and that `enforce_schema` drops the split key, reorders to canonical order, and warns rather than silently padding.

### Two-stage risk ranking

`/api/v1/customers/risk` does **not** rank the cohort by hazard alone. It takes the 200 highest-volume contributors, scores them in one batched Cox inference, and returns the 20 with the highest hazard.

Ranking the full cohort by hazard produces garbage: the most confidently-lapsing contributors are drive-bys, and a retention queue of people who filed three issues and left is not something any maintainer would action. Ranking by volume alone returns whoever is busiest regardless of risk. The intersection is the only actionable set.

## Presentation Layer

Next.js 16 (Turbopack), React 19, TypeScript strict with zero `any`, Tailwind v4, Recharts 3.

Four decoupled tabs: **Command Suite** (cohort KPIs), **ML Engine** (registry drift, lineage, telemetry), **Retention** (triage queue + threshold simulator), **Platform & Governance** (dbt health, model card).

The triage queue translates the model for non-technical readers. Urgency bands are computed from `median_survival_days`, **not** hazard ratio — a hazard ratio is relative to a cohort baseline and 1.12× reads as "12% worse" when it actually means ~95 days:

| Band | Median survival | Copy |
| --- | --- | --- |
| Critical | ≤ 30 days | "Lapses in ~3 weeks" |
| Elevated | 31–90 days | "~2 months left" |
| Watch | 91–180 days | "Slow decline" |
| Stable | never reached | "No lapse projected" |

Copy is deliberately approximate — "~3 weeks", not "27 days". A holdout C-index of 0.70 supports ranking, not calibration; false precision is a claim the metric cannot back.

Each row carries an inline Kaplan-Meier sparkline on a **fixed `[0,1]` domain**. Without the fixed domain, Recharts auto-scales each row independently and a contributor decaying 1.00 → 0.98 draws the identical cliff to one collapsing to 0.20.

**Mock elements are labelled as mock.** The telemetry feed is badged `simulated`. The outreach drafter templates client-side and states that nothing is sent. Failed sparkline fetches return empty arrays, never fabricated series.

## Notable Findings

### STL recovered the US holiday calendar from raw event volume

Decomposing daily activity with `period=7` and flagging 3σ residuals — *after* weekly seasonality and trend are removed — surfaces five days across 184:

```
2023-07-04   collapse   z = -3.95    US Independence Day
2023-09-05   collapse   z = -4.16    day after Labor Day
2023-10-18   collapse   z = -3.04
2023-11-24   collapse   z = -4.42    day after US Thanksgiving
2023-12-19   spike      z = +3.70
```

The deepest collapses are US public holidays. **No calendar was supplied to the model.**

### Cohort retention is triangular by construction

`metric_contributor_retention` emits a cell only where activity was observed:

```
Jul 2023   n=16,872   100% → 12.05% → 9.02% → 8.17% → 7.40% → 6.74%
Aug 2023   n=12,918   100% →  8.10% → 5.27% → 4.75% → 3.75%
Sep 2023   n=12,505   100% →  7.66% → 4.77% → 3.89%
Oct 2023   n=12,318   100% →  6.50% → 3.72%
Nov 2023   n=11,837   100% →  5.96%
Dec 2023   n=10,845   100%
```

Zero-filling the empty upper-right is the classic error: it reports "0% retained" for periods never observed, dragging every recent cohort's curve to the floor. **Absent means unobserved, not churned.**

## Known Limitations

- **607 holdout rows.** A ±0.02 swing in C-index is inside sampling noise. Do not quote 0.7005 as precise; widening the repo cohort or the observation window is the only way to shrink that error bar.
- **Hyperparameter search has converged.** Two successive grid expansions moved holdout score by −0.001. Remaining headroom is in the data, not the tuning.
- **The Breslow baseline assumes proportional hazards.** No formal test of the proportionality assumption (Schoenfeld residuals) has been run. The Kaplan-Meier terciles do not cross, which is suggestive but not proof.
- **Two models serve one dashboard.** The threshold simulator is probability-based and the triage queue is hazard-based. Both are honest; the coexistence is not yet explained in the UI.
- **`metric_activity_decomposition` is written by Python, not dbt.** `dbt build` will not rebuild it — `decompose_activity.py` must run after every landing.
- **CI lints and runs contract tests only.** The dbt leakage test requires a real warehouse and is documented as a local step; synthesising a fixture to make it green would defeat its purpose.
